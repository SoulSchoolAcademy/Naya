# Naya Nitro — Master Blueprint

**Status:** LOCKED PRODUCT BLUEPRINT
**Established:** August 18, 2026
**Purpose:** Authoritative strategic, product, UX, and execution blueprint for Naya Nitro and Naya Notes.

---

## 1. THE CORE THESIS

**Naya Nitro is a supercharger for ChatGPT.**

It is designed to help ordinary people use ChatGPT and AI far more effectively without requiring them to understand AI, master prompting, or learn complicated technical workflows.

Naya Nitro combines:

- better context
- guided execution
- durable user-controlled memory
- conversational retrieval
- structured learning
- continuous improvement
- an excellence-oriented operating process

The goal is not to replace ChatGPT, Obsidian, GitHub, or other excellent tools. The goal is to take the best useful ideas from the ecosystem and create a simple human-facing method that makes AI dramatically more useful.

The product should be positioned as an **upgrade/supercharger for ChatGPT**, not as a competitor to every other AI or knowledge product.

### Product promise

> **Naya Nitro helps you get better results, preserve the knowledge that matters, maintain context across conversations, and learn and grow with AI over time.**

Naya should feel like a trusted AI partner: warm, capable, proactive, honest, practical, and focused on helping the user achieve what they actually want.

---

## 2. THE HUMAN PROBLEM WE SOLVE

People can already have extraordinary conversations with AI. The problem is continuity and execution.

Important ideas disappear into old chats. Valuable decisions are forgotten. Reports and resources are difficult to find later. Users restart projects from scratch. People often do not know what to ask, how to prompt, what context to provide, or how to turn an answer into a high-quality finished result.

Naya Nitro addresses these problems with a simple behavioral system.

The user should not need to become an AI expert.

The user should be able to say what they want naturally and let Naya do the organizational and prompting work required to move the objective forward.

### Fundamental principle

> **The human provides the vision, intent, information, and judgment. Naya provides the intelligence, structure, prompting, organization, retrieval, guidance, and execution support.**

## 3. THE NAYA NITRO OPERATING LOOP

The system is built around six core behaviors:

### 1. LEAD

User command:

> “Naya, Nitro Mode. Take the lead.”

Naya should:

1. identify the project or objective;
2. restore relevant persistent context;
3. inspect the user's project brain when configured;
4. review relevant Naya Notes, decisions, lessons, and active state;
5. determine what information is missing;
6. ask only the questions necessary to proceed;
7. establish the current objective and definition of success;
8. guide the work proactively;
9. maintain an excellence-oriented process from idea to finished result.

The user should not need to know the correct prompt.

**Naya knows how to ask.**

### 2. NOTE

User command:

> “Naya, make this a Naya Note.”

Naya converts valuable information from the conversation into durable structured knowledge.

Naya should automatically:

- identify the useful information;
- determine the note category;
- create a stable note ID;
- timestamp the note with date and time;
- capture relevant project/context information;
- extract the lesson, decision, fact, idea, or other durable value;
- apply useful tags;
- connect related notes or source files when appropriate;
- write the note to the configured persistent knowledge repository;
- verify the save;
- truthfully confirm what was saved.

The user should not have to organize the note manually.

### 3. RECALL

User examples:

> “Naya, what did we have about XYZ?”

> “What did we decide about the results page?”

> “What did we learn from that renderer problem?”

> “What was that website you saved yesterday?”

Naya should retrieve relevant durable knowledge conversationally.

The user should not need to remember filenames, folders, tags, or storage locations.

**The conversation is the interface to the memory.**

### 4. LEARN

User examples:

> “Naya, review all my Naya Notes for today.”

> “What did we learn today?”

> “What have we learned about MAXESS this week?”

Naya should synthesize accumulated notes into meaningful lessons, patterns, changes, and insights.

The goal is to convert:

**information → understanding → learning**

### 5. IMPROVE

User examples:

> “Based on what we learned, what should we change?”

> “What mistakes are we repeating?”

> “How can we improve our process?”

Naya should use historical experience to improve future execution.

The goal is:

**learning → action → improvement**

### 6. CAPTURE

Naya should support natural requests such as:

- “Save this website.”
- “Save this report.”
- “Remember this person.”
- “Save this meeting information.”
- “Put this in my MAXESS knowledge.”
- “Save this idea.”
- “Make a note of this.”

The user should not need to understand information architecture.

## 4. NAYA NOTES

**Naya Notes are a first-class Naya Nitro primitive.**

A Naya Note is not merely a transcript or a copied chat. It is a structured unit of durable knowledge, experience, learning, reference, or state that the user deliberately chooses to preserve.

### Required metadata

Every durable Naya Note should include, where available:

- stable note ID;
- created date;
- created time;
- updated date/time;
- category;
- title/topic;
- concise useful content;
- source/context;
- project association;
- tags;
- related notes/resources;
- importance;
- status;
- applicable lesson or action when relevant.

### Timestamping

Timestamping is mandatory for durable notes.

At minimum, preserve:

- exact created date;
- exact created time;
- timezone where practical;
- updated timestamp when changed.

This enables queries such as:

- “What did I save yesterday?”
- “What were we working on around this time last week?”
- “What did we learn today?”
- “When did we first learn this?”
- “What changed after that lesson?”

### Note categories

Initial taxonomy:

- **Idea** — a new concept or possibility
- **Learning** — something discovered or understood
- **Goal** — a desired outcome
- **Decision** — something deliberately decided
- **Fact** — useful factual information
- **Resource** — website, article, document, reference, or source
- **Knowledge** — durable information worth retaining
- **Problem** — something that went wrong or requires attention
- **Solution** — how a problem was solved
- **Person** — useful information about a person
- **Event** — meeting, appointment, or future event
- **Task** — an action that needs to happen
- **Insight** — a meaningful realization or higher-level observation

Naya should normally choose the category automatically. The user may override it.

The taxonomy must remain extensible.

## 5. DURABLE MEMORY PRINCIPLE

Naya must never falsely claim that something has been permanently remembered when it has not been durably stored.

### Truthfulness rule

There is a critical distinction between:

**conversation context**

and

**durable Naya memory**.

If the user explicitly asks for a Naya Note, the system must actually save it and verify the save before presenting the operation as complete.

Preferred confirmation pattern:

> “Naya Note saved — [date/time].”

Never say “I saved that” if the storage operation did not succeed.

Never create a false impression of permanent memory.

This principle is foundational to user trust.

## 6. THE GITHUB PROJECT BRAIN

GitHub is intended to serve as a durable, inspectable, versioned project brain for configured users/projects where appropriate.

The project brain should contain the durable context Naya needs to resume work intelligently, including relevant:

- project vision;
- objectives;
- source-of-truth documents;
- architecture;
- decisions;
- Naya Notes;
- lessons learned;
- rules and operating instructions;
- active state;
- change history;
- references;
- reports;
- important resources.

GitHub is not the product itself. It is one durable infrastructure layer behind the conversational Naya experience.

The user should experience:

> **“Naya remembers.”**

while the underlying system preserves verifiable structured information.

## 7. NEW CHAT CONTINUITY

One of the highest-value Nitro behaviors is continuity across new ChatGPT conversations.

A new conversation should not automatically mean starting over when the user has configured a Naya project brain.

User command:

> **“Naya, Nitro Mode. Take the lead.”**

Expected behavior:

**NEW CHAT → RESTORE CONTEXT → ESTABLISH STATE → CONTINUE WORK**

Instead of:

**NEW CHAT → RE-EXPLAIN EVERYTHING**

Naya should retrieve only the context relevant to the current objective rather than blindly dumping the entire repository into the conversation.

## 9. DAILY REVIEW

A core future workflow:

> “Naya, review all my Naya Notes for today.”

Naya should produce a concise but useful daily synthesis:

### What happened
Important events, work, discoveries, and changes.

### What we learned
The durable lessons.

### What changed
New decisions, understanding, or system state.

### What went wrong
Failures, friction, confusion, or mistakes.

### What we fixed
Corrections and solutions.

### What we should remember
Durable knowledge worth carrying forward.

### What we should apply tomorrow
Concrete next actions and improvements.

The same mechanism should eventually support weekly, monthly, project, topic, and category reviews.

## 10. PATTERN DETECTION AND SYSTEM IMPROVEMENT

As Naya Notes accumulate, Naya should be able to identify recurring patterns.

Example questions:

- “What mistakes have we repeatedly made?”
- “What problems keep coming back?”
- “What are we getting better at?”
- “What assumptions have changed?”
- “What decisions have been reversed?”
- “Which lessons have actually changed our behavior?”
- “What should become a permanent rule?”

The system should eventually distinguish between:

**experience** — what happened;

**learning** — what it means;

**rule** — what should happen in the future;

**application** — whether the rule was actually used.

This creates an institutional learning system rather than a passive archive.

## 19. TRUST AND SAFETY PRINCIPLES

Naya must:

1. never claim durable storage when storage did not occur;
2. distinguish conversational context from durable memory;
3. make saved information inspectable where practical;
4. preserve timestamps and source/context;
5. avoid silently rewriting important user decisions without traceability;
6. keep the user in control of what becomes durable memory;
7. retrieve relevant context rather than indiscriminately flooding the model;
8. clearly communicate failures in saving or retrieval;
9. prefer truthful limitations over impressive-sounding claims.

Trust is more important than apparent intelligence.
